Support at each milestone

Four technical phases: SRS, design, prototype and final delivery

Bring the template and marking requirements supplied by your university. Each phase should connect requirements to design decisions, working features and evidence from tests.

Phase 1 · Requirements

Software Requirements Specification (SRS)

Define the problem, stakeholders, scope, actors and use cases. Separate functional requirements from security, performance and other non-functional requirements. Record assumptions, dependencies and measurable acceptance criteria.

Bug-hunting example: specify authorized APK input, supported analysis scope, report fields and failure cases. Distinguish static findings from issues that require manual validation.

Review output: a requirements checklist and traceability IDs that can be mapped to design and tests.

Phase 2 · Architecture

Design Document

Map requirements to components, interfaces, data flows and database entities. Review use-case, sequence and deployment diagrams, API contracts, authentication, error handling and trust boundaries.

Bug-hunting example: separate APK intake, analysis workers, findings storage and reporting. Define safe file handling, worker isolation and authorization for any device interaction.

Review output: a coherent architecture and module plan that explain how each requirement will be implemented.

Phase 3 · Working slice

Prototype and Implementation

Set up the development environment, pin dependencies, implement a small end-to-end workflow and test it with representative inputs. Debug reproducible errors before expanding features.

Bug-hunting example: demonstrate a permitted sample APK moving through intake, one scoped analysis step and a basic report. Label fixture results and avoid presenting a prototype as a complete vulnerability scanner.

Review output: a runnable prototype, setup instructions, test inputs and an explicit list of limitations.

Phase 4 · Verification

Final Delivery and Viva Preparation

Trace tests back to SRS requirements. Check integration, negative inputs, access controls and recovery paths. Prepare installation instructions, a user guide, known issues, a reproducible demonstration and a clean source package.

Bug-hunting example: explain false positives, unsupported APKs, analysis failures and the boundary between automated findings and validated vulnerabilities.

Review output: a submission checklist, test evidence and practice explaining your own technical decisions.

These are illustrative milestones for the proposed Intelligent Bug Hunting Platform, not claims of completed deliverables. You write and submit your own assessed work; support focuses on review, understanding and troubleshooting.
